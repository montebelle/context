# Go-to prompt library

Reusable base prompts for the `prompt` skill. Invoke one by its slug or by clear intent (e.g. "run my verify-work prompt on this repo") and the skill loads the entry below as the base, then routes it through the normal rewrite — grounding it to the current repo and harness, compressing it, and naming the completion evidence — so you never re-paste the wall of text. These are raw source prompts: the skill improves them, it does not run them verbatim, and it never executes the result without a separate request.

Each `##` heading is a slug. Bodies are canonical — edit them here to change the go-to.

## verify-work

Double-check the completed work across the entire folder or repository. Inspect the relevant directories, files, code, configuration, tests, scripts, notebooks, schemas, prompts, data pipeline logic, agent or harness logic, dependency files, logs, and supporting assets needed to verify the implementation. Do not assume the work is correct because it was already completed. Verify the actual code and outputs directly against the stated goal, requirements, expected behavior, and any prior findings or requested changes. Check for missed files, incomplete edits, regressions, broken integrations, inconsistent updates, hidden assumptions, duplicated logic, edge case failures, incorrect outputs, and places where the implementation does not match the intended result. Confirm what was completed successfully, what remains incorrect or unverified, and whether any new issues were introduced. For each issue, identify the affected location, what is wrong, why it matters, and the clearest corrective improvement. Do not make unsupported claims. Clearly state anything that cannot be confirmed from the available files. Do not produce .md or .txt files.

## code-review

Conduct a thorough review of the code for this project, adapting the review to whatever type of project it is, including application code, machine learning, data pipelines, agents, evaluation harnesses, OpenCLAW-style systems, notebooks, libraries, APIs, CLIs, or mixed repositories. Review every relevant file, function, class, configuration, workflow, and execution path for correctness, methodological soundness, reproducibility, maintainability, and performance. Identify any arbitrary constraints, hidden assumptions, logical errors, inconsistencies, duplicated logic, redundant computations, dead code, unreachable paths, edge case failures, inefficient implementations, brittle abstractions, unsafe defaults, or other technical defects. Verify all formulas, transformations, feature engineering, statistical methods, model logic, evaluation metrics, agent behavior, tool-use logic, orchestration flow, joins, aggregations, indexing, time alignment, parameterization, and configuration choices. Check for data leakage, target leakage, evaluation leakage, benchmark contamination, double counting, incorrect joins, aggregation errors, schema mismatches, state contamination, nondeterminism, reproducibility issues, and train/test or temporal misalignment. Confirm the implementation is mathematically, statistically, and methodologically appropriate for its purpose. Where issues are found, explain the problem, why it matters, the affected location, the likely consequence, and the clearest corrective improvement. Do not produce .md or .txt files.

## research

Search the web for credible, high-quality research and trusted technical sources relevant to the system being reviewed. Adapt the search to the project type, including software, machine learning, data pipelines, agents, evaluation harnesses, OpenCLAW-style systems, APIs, libraries, infrastructure, or mixed codebases. Prioritize peer-reviewed papers, landmark or recent studies, standards bodies, government sources, academic institutions, official documentation, benchmark papers, reproducibility studies, and leading engineering publications. Prefer sources with clear methodology, empirical validation, reproducible results, statistical or experimental support, and stated limitations. Avoid opinion pieces, marketing content, weak blogs, unsupported claims, outdated guidance, and sources without clear evidence. Assess each source for credibility, relevance, methodological soundness, and applicability to the current task. Summarize the key validated insights, evidence, limitations, and practical best practices. Clearly separate established evidence, emerging research, industry convention, and uncertainty. Use the sources to support concrete recommendations, and do not make claims that cannot be verified from reliable sources or the codebase itself.

## logs-audit

Check all available system, application, training, pipeline, agent, harness, and execution logs for errors, warnings, failures, retries, partial runs, resource limits, dependency conflicts, performance degradation, and anomaly indicators. For each issue found, identify the timestamp, component, execution stage, root cause, downstream impact, and whether it was resolved or remains an active risk. Look for silent failures, suppressed exceptions, incomplete outputs, skipped steps, unstable behavior, data/model integrity risks, and reliability problems. Recommend precise corrective and preventive actions tied to each issue. Do not guess when logs are incomplete; clearly state what can and cannot be verified from the available evidence.

## readme-sync

Check all available Git commits, pull requests, merge diffs, dependency updates, configuration changes, file additions or removals, renamed modules, interface modifications, environment variable updates, and execution workflow revisions for any functionality, requirements, commands, setup steps, architectural changes, or operational behaviors that are missing, outdated, inconsistent, or inaccurately represented in the current README. Identify the exact commit hash, timestamp, author, affected component, and development stage associated with each discrepancy; determine the root cause of the documentation drift and the downstream impact on installation, configuration, usage, deployment, or developer onboarding; and generate precise README updates that fully synchronize documentation with the present repository state. Confirm whether each identified documentation gap has been corrected or remains an active risk, and flag any undocumented features, deprecated instructions, ambiguous steps, or silent behavioral changes that could compromise usability, reproducibility, or system reliability.
